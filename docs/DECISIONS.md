## 三、缓存策略冲突分析（PRD 第6节 vs ZHIHU-API.md）`[已确认 2026-08-27]`

**冲突点**：PRD 第6节（第145/147行）与 API 文档给的 TTL 不一致。

| 接口 | PRD 第6节要求 | ZHIHU-API.md 给的 | 是否冲突 |
|---|---|---|---|
| 搜索(zhihu_search/global_search) | 按"身份+关键词"缓存 **3 天** | TTL **1 小时**（按 query hash） | ⚠️ 冲突（PRD 更长） |
| 故事/回答 API | 按关键词缓存 **7 天** | 无独立"故事 API"；直答 agent_answer TTL 1 小时 | ⚠️ 部分冲突 |
| 热榜 hot_list | PRD 未明确 | TTL **4 小时**，每日拉一次 | — |
| 直答 chat/completions | PRD 未明确 | TTL **1 小时**（按 query hash） | — |

**决策：以 PRD 第6节为主（最大程度按 PRD 要求处理）。** 即搜索缓存 3 天、回答缓存 7 天。

**为什么和 API 文档不同？能否解决？**
- 原因：API 文档的 TTL 是"知乎官方建议的防抖窗口"（避免短时间重复打接口）；PRD 的 3天/7天是"产品层业务缓存"（用户处境几天内不变，不必重拉）。两者目的不同，**不矛盾，可叠加**。
- 解决方式：实现上采用**双层缓存**——
  1. **业务缓存（PRD 为准）**：搜索结果按"身份+关键词"存 3 天、回答存 7 天，命中直接返回，不触接口；
  2. **接口层兜底（API 文档为准）**：即便业务缓存失效，调用前仍检查 API 文档的 1 小时/4 小时最小窗口，避免单品类每天超 1 次拉取、热榜超 100 次/天。
  - 这样既满足 PRD"缓存 3/7 天"的体验要求，又不突破 API 文档的官方配额与防抖建议。
- 备注：PRD 第6节写"单品类每天仅 1 次拉取最新内容"——与 API 文档"搜索 5000次/天"不冲突（1次/天是产品节流，远低于 5000 上限）。`zhihu.js` 现有简易文件缓存需补充"按身份+关键词"维度与 3/7 天 TTL。
