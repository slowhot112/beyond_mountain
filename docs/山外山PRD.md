1. 文档概述

版本：v1.1（黑客松 MVP 版）

目标：3 天内完成可演示的求职决策 Demo，实现「知乎真实经验 → 处境化筛选 → 一步步求职行动规划」的核心流程

适用范围：知乎开放平台黑客松参赛作品


2. 产品定位与核心价值

一句话定位：把知乎上海量的"过来人求职经验"按用户当下处境重新组织，陪用户看清自己站在哪座山、并一步步迈出求职的第一步，实现「被动刷经验 → 处境化匹配 + 可执行行动」。

核心价值：

对用户：用"翻山"的隐喻把混乱的求职信息变成一条属于自己的登山路线，降低决策焦虑，提升行动启动率

对社区：为知乎优质职业内容提供新的消费形态（从"看回答"到"被推荐给处境相似的人"），提升内容分发效率与用户停留时长

对赛事：完全覆盖赛事重点鼓励的「知乎 IP 衍生 AI 应用、真实数据驱动个性化」高创新加分方向，并以"刘看山"IP 形象强化知乎生态贴合度


3. 目标用户画像

用户分层	特征	核心需求

18-25 岁应届生	面临升学/就业/ Offer 选择，信息过载	在海量经验里快速找到"和我处境一样的人"

25-35 岁职场人	考虑转行、转型或在职深耕，时间碎片化	用最少时间判断"这条路适不适合我"

知乎深度用户	熟悉社区内容，愿意分享决策经历	有真实经验可沉淀、可分享到知乎社区


4. 核心功能模块

模块 1：处境定位（渐进式处境建档）

职责：用尽量少的输入形成一张可编辑的“处境卡”，把用户圈定到“和自己最像的那群登山者”，作为经验匹配、观点对照与行动规划的统一输入。

设计原则：

- 先问影响推荐最大的条件，再按需追问，避免一上来让用户填写长表单。
- 简历负责回答“我是谁”，用户补充回答“我想去哪、现在卡在哪里”。
- 所有 AI 提取结果必须由用户确认后才能用于推荐；不上传简历也能完整使用产品。

建档流程：

1. 选择当前阶段（单选）：在校探索 / 应届求职 / 待业求职 / 在职观望 / 在职深耕 / 转行转岗 / Offer 决策。
2. 选择当前目标（可多选）：找实习 / 找全职 / 换公司 / 换岗位 / 换行业 / 升学与就业决策 / 比较 Offer / 暂未明确。
3. 可选上传简历：MVP 支持 PDF、DOCX，AI 提取教育经历、工作或项目经历、技能、所在行业等结构化字段。
4. 用户确认并修改提取结果；系统仅追问简历无法提供的信息：目标岗位、目标行业、目标城市、期望时间及当前最困惑的问题。
5. 未上传简历的用户通过 3–5 个轻量问题补全关键信息。
6. 生成可编辑的“处境卡”，展示系统将使用的匹配条件，用户确认后进入内容推荐。

处境卡核心字段：

| 字段 | 是否必填 | 来源 | 用途 |
|---|---|---|---|
| 当前阶段 | 是 | 用户选择 | 确定基础内容池 |
| 当前目标 | 是 | 用户选择 | 确定问题类型与行动方向 |
| 教育与经历摘要 | 否 | 简历提取 / 用户填写 | 匹配背景相似者 |
| 目标行业与岗位 | 否 | 用户填写 | 收窄经验范围 |
| 目标城市 | 否 | 用户填写 | 匹配地域相关经验 |
| 时间压力 | 否 | 用户填写 | 调整行动计划粒度 |
| 当前困惑 | 是 | 用户填写 | 生成检索词与观点对照主题 |

MVP 边界：简历上传仅用于结构化信息提取，不提供简历评分、润色、岗位胜任力结论或自动投递；文件解析失败时提示用户改用手动建档。

模块 2：知乎真实经验接入

职责：从知乎拉取与用户处境相关的真实回答与文章，作为决策依据

内容来源：

知乎搜索 / 内容 API：按"行业 + 处境关键词"拉取高赞职业问答（如"本科毕业 工作还是读研""转行 要不要报班"）

知乎故事 / 回答 API：拉取第一人称经历型内容，保留原作者的真实处境描述

内容筛选规则：

优先选"信息密度高、含明确处境条件"的内容（有保研资格吗、Offer 水平、家庭压力等），便于后续做处境匹配

复用仓库能力：concepts/AI 信息量最优区间（筛选高密度内容，降低后续 AI 整理成本）

模块 3：🎯 为你推荐（处境化匹配引擎）

职责：把知乎真实经验按用户筛选条件重新排序，把"真的值得参考的人"摆到用户面前

设计逻辑：

结合处境卡字段 + 知乎真实热度，推送与用户当前阶段、目标和困惑最相关的经验与数据

强调"可溯源"：每条推荐标注它来自哪个知乎回答、匹配了用户的哪个筛选条件（参考 ArguMesh 的证据溯源设计，详见第 11 节）

模块 4：求职行动规划（一步步上路）

职责：不替用户决定翻哪座山，而是把求职拆成可执行的小行动

设计逻辑：

看清脚下：帮用户定位当前站在哪座山、脚下是什么路况

铺出路径：把"求职"这件大事拆成一步步行动清单（如：梳理自身条件 → 圈定目标方向 → 准备 1 份对标简历 → 发起 3 次 informational interview）

陪他上路：在每一座山前持续提示、校准方向，直到用户真正动身

模块 5：沉浸式工牌入口（刘看山 IP）

职责：用知乎看山 IP 形象"刘看山"作为叙事引导角色，提供有仪式感的起点

设计：

可拖拽晃动的 3D 工牌（React + Three.js 物理引擎），下拉 / 滚动即进入主流程

用刘看山"翻越一座座没有尽头的大山"的隐喻贯穿产品，强化知乎社区风格


5. 完整用户交互流程


否

是

1. 用户选择当前阶段与目标。
2. 用户选择上传简历或手动回答轻量问题。
3. 系统提取并展示处境信息，用户确认或修改，生成“处境卡”。
4. 系统按处境卡生成检索词，拉取知乎真实经验。
5. AI 按处境匹配度与内容热度排序，生成“为你推荐”。
6. 用户浏览推荐经验与观点对照，查看来源和匹配条件。
7. 用户主动点击“生成行动路线”，系统基于处境卡与已浏览内容生成行动清单。
8. 用户完成第一步、记录反馈；系统据此校准后续行动与推荐。

关键分支：

- 用户跳过简历：进入手动建档，不阻断主流程。
- 简历解析失败：保留已填写信息并切换到手动建档。
- 用户暂未明确目标：先推荐用于探索方向的经验，不强行生成具体岗位行动计划。


6. 知乎 API 对接方案

使用 API	调用场景	限制应对方案

知乎内容 / 搜索 API	拉取与用户处境相关的职业问答	按"身份 + 关键词"缓存 3 天，单品类每天仅 1 次拉取最新内容

知乎故事 / 回答 API	拉取第一人称经历型内容	按关键词缓存 7 天，仅拉取高赞内容，单用户每日上限内完全够用

7. 技术架构设计

前端：使用前端框架（Vue 或 React，待定）。框架负责渐进式建档、处境卡确认、观点对照墙、自测与行动地图的渲染与交互；构建产物由 Node 后端托管。

数据层：知乎官方 API 经 Node 后端代理 + 文件缓存（Secret 缺失时自动降级 Mock 演示数据，保证"打开即完整"）

简历解析：后端接收 PDF / DOCX，完成文本提取后调用大模型输出受约束的结构化字段；原始文件在解析完成后删除，前端只保存经用户确认的处境字段

推荐引擎：大模型基于处境卡做内容匹配与行动规划，每条输出带"来源回答 + 匹配条件"溯源字段

缓存机制：种子内容、生成的推荐节点全部缓存，避免重复调用 API 与重复生成

内容审核：接入知乎内容审核规则，避免生成违规内容


8. 参考开源项目（含真实落地状态）

我们参考了 7 个论证 / 辩论类开源项目（GitHub 已核验），取其"呈现对立视角、不替用户下结论"的方法论内核。下面区分**已实现借鉴**与**计划借鉴但未做**，如实记录，避免包装。

参考项目清单（相似点 / 差异）：

| 项目 | 链接 | 与我们相似点 | 差异 |
|---|---|---|---|
| both-sides-research | https://github.com/PSkinnerTech/both-sides-research | 钢人论证呈现对立最强论据，不丑化对方 | 它最终仍给结论；我们坚持不替用户定论 |

8.1 已实现借鉴（有真实代码支撑）

（1）钢人论证对峙墙 — 借鉴 both-sides-research

- 怎么做：后端 `zhihu.js` 的 `alchemy()` 在给知乎直答的 prompt 中强制要求"用钢人论证呈现他的最强论点，必须落到具体行业场景，不要丑化对立面"（详见 prompt 第 162 行）；同时强制每个角色 rebuts 至少质疑另一角色，形成交锋。
- 实现多少：100% 接入生成流程；前端 `app.js` 第 329–377 行已渲染多角色卡片（最强论点 / 适合谁 / 边界 / 互相质疑），并支持翻面看来源文章。
- 解决需求：把知乎上互相矛盾的回答变成"同一个刘看山分裂成几种样子在辩论"，让用户一眼看清分歧而非被单一高赞带节奏。
- 隐患：钢人论证质量依赖直答模型能力；当直答返回角色数 <2 或不守 JSON 时，本地 `topicMock` 兜底补全（可能用通用三派而非真实行业派别，存在"假对峙"风险）。

（2）不综合、留白给用户 — 借鉴上述全部项目的反向差异点

- 怎么做：prompt 第 189 行明确"不要综合成单一结论，保留派别之间的张力"；前端不渲染任何"推荐答案"。
- 实现多少：100% 落实在生成与展示层。
- 解决需求：训练用户自己的判断，而非喂结论。
- 隐患：部分评委/用户可能期望"给个结论"，需要文案引导理解产品哲学。

（3）判断力自测（魔鬼辩驳思路）— 借鉴 devils-advocate

- 怎么做：生成结果含 `quiz`（逼用户选立场 + 写理由 + 看反馈）；前端第 399–430 行实现单选 + 文本输入 + 反馈展开，并 `recordSide` 记录偏好。
- 实现多少：自测交互 100% 实现；但"魔鬼辩驳"目前是 LLM 在生成时一次性产出反馈文案，并非运行期实时针对用户填写内容做对抗追问（属于"静态自测"而非"动态辩驳"）。
- 解决需求：逼用户产出自己的立场，而非选知识正确答案。
- 隐患：反馈是生成时写死的，不会因用户具体回答而变化，训练深度有限。

（4）知乎真实数据接入 — 区别于所有参考项目（它们多接本地/论文，零知乎关联）

- 怎么做：后端 `server.mjs` 代理知乎搜索/热榜/直答 API，Secret 仅存后端；`zhihu.js` 含文件缓存 + Mock 兜底；前端首屏即拉真实推荐。
- 实现多少：搜索/热榜/直答/alchemy 四接口可用；Secret 缺失时自动降级演示数据，保证"打开即完整"。
- 解决需求：内容源是活的知乎社区，而非静态文件。
- 隐患：依赖你提供的 Access Secret 是否有效及配额；LIVE 下直答超时/额度耗尽会回落 Mock（已在代码中标 fallback 提示）。

（5）处境卡 × 8 行业 × 细分筛选 — 产品自有，无直接对应参考

- 当前实现：personas.js 配置 + 前端 mega menu 已实现原有三角色与职业筛选，选职业后自动重炼。
- 本版调整：扩展为“当前阶段 + 当前目标 + 可选简历 + 轻量追问”的渐进式建档；处境卡确认与简历解析属于待实现项。
- 解决需求：把"泛经验"收窄到"和我处境像、目标也相近的人"。

8.2 计划借鉴但未做（诚实标注）

（1）流式渲染 + 截图/打印导出 — 借鉴 DialecticEngine

- 打算怎么做：结果分块流式输出（SSE）；加"导出图片/截图"按钮。
- 为什么还没做：步骤未到，当前为一次性返回 + 已有 Markdown 导出与 `window.print()`，够演示；流式需在后端改造直答调用为流式，工作量中等。
- 预计功能：长结果边生成边看，避免等待；一键生成分享图。
- 预计解决需求：提升"打开即可见对峙成品"的体验与可传播性。
- 预计隐患：流式中断处理复杂；截图需处理跨域图片。
- 预计卡点：后端直答需支持 stream，且前端要兼容非流式降级。

（2）真实多 Agent 并发辩论 — 区别于当前"伪多 Agent"

- 当前做法：单次调用让模型扮演多角色（零额外额度），非真并发。
- 打算怎么做：多个 Agent 并行调用知乎直答，各自持不同立场再汇总对峙。
- 为什么还没做：技术可行但**额度成本高**（每次生成 N 倍调用），在 Secret 配额有限下不划算；属于"增强项"非"必需项"。
- 预计功能：角色立场更独立、更少互相抄袭，对峙更真。
- 预计解决需求：提升对峙墙的真实交锋感。
- 预计隐患：多倍 API 消耗、延迟叠加、角色间一致性难控。
- 预计卡点：配额与成本，是主要拦路石。

（3）OAuth 真实接入（连接知乎账号 → 信息宇宙分析）— 借鉴 multi-agent-debate 的"用户上下文"思路

- 当前做法：`oauth.js` 已实现授权流程骨架，但默认 MOCK 模式（localhost 无法完成公网 HTTPS 回调）。
- 打算怎么做：部署到公网 + 配置真实 app_id/app_key，读取用户关注/粉丝生成偏好图谱。
- 为什么还没做：**技术限制**——OAuth 回调要求公网 HTTPS，本地 dev 跑不通；非步骤未到，而是环境约束。
- 预计功能：基于真实社交关系做"信息宇宙"个性化。
- 预计解决需求：从"按职业筛选"升级到"按你真实关注圈筛选"。
- 预计隐患：知乎 OAuth 接口实测 schema 不完整（文档仅提示），接入后可能踩坑。
- 预计卡点：必须公网部署，且需真实应用凭证。


9. 风险评估与应对

风险	概率	应对方案

AI 推荐跑题 / 不匹配	中	预设身份锚点与处境关键词，生成后做匹配度校验，偏离自动重写

溯源标注缺失	中	在推荐引擎输出结构里强制要求"来源 + 匹配条件"字段，缺失则回退到原始回答链接

API 调用超限	低	种子内容提前缓存，仅用户主动触发时调用 API

工牌 3D 性能问题	低	限定物理计算复杂度，移动端降级为静态工牌图

OAuth 卡在公网环境	高（确定）	本地仅演示 MOCK；演示/评审以"职业筛选 + 对峙墙"为主线，OAuth 作为可选增强说明

简历包含敏感个人信息	高	上传前明确用途；仅解析必要字段；原始文件解析后删除；用户确认后才进入推荐；提供清空处境数据入口

简历解析错误或格式不兼容	中	限制 PDF / DOCX；展示结构化结果供用户确认；失败时无损切换为手动建档

建档步骤过长导致流失	中	仅当前阶段、目标和困惑必填；简历上传与其余字段可跳过；展示步骤进度并允许稍后补充


9.1 MVP 范围与验收标准

3 天内必须完成：

- 当前阶段与目标选择。
- 手动轻量建档与可编辑处境卡。
- PDF / DOCX 简历解析演示链路，至少支持预设样例稳定演示；解析失败可降级手动填写。
- 基于处境卡的知乎内容筛选、匹配理由与来源展示。
- 基于处境卡生成一份可执行行动清单。

不纳入本次 MVP：简历评分与润色、自动投递、实时多 Agent、完整 OAuth、复杂用户画像长期存储。
