# 山外山可复刻开发 SOP

> 这是一份可以交给新队友、从零复刻主流程的执行手册，不是产品介绍。

## 0. 完成定义

复刻成功必须跑通：

    提出困惑
    → 最少建档
    → 返回真实来源
    → 展示不同处境的判断
    → 用户形成暂时判断
    → 完成一个小验证
    → 回填现实
    → 用户确认是否改变判断
    → 影响下一次使用

完成标准：

- 新用户不看说明也能走完第一条路径。
- 真实来源都有可打开 URL。
- AI 内容不会冒充知乎原文。
- 每个按钮点击后都有可见结果。
- 历史记录不会静默覆盖或自动改写。
- 390px、768px、桌面宽度都能完成主流程。
- 本地、构建、公网部署均可复现。

## 1. 开工前建立四份文件

在 docs/ 建立：

- PRD.md：用户、问题、定位、主流程、明确不做什么。
- DECISIONS.md：每个关键选择、原因、影响和验收方式。
- UX-FLOW.md：页面状态和状态转移。
- TEST-MATRIX.md：正常、空结果、失败、重试、历史、登录等场景。

每条决策统一使用：

    D-001：历史判断不能自动套用
    状态：已确认
    决策：相似处境只展示候选，必须由用户确认后带入。
    原因：避免旧结论误导新问题。
    验收：未确认时，本次请求不携带旧记录。

## 2. 先冻结产品不变量

在写 UI 之前确认：

1. 来源真实且可打开。
2. AI 只整理，不冒充原作者。
3. AI 不替用户做关键决定或对外行动。
4. 现实证据只能提出变化。
5. 变化必须由用户确认后进入长期记忆。
6. 每个页面只承担一个主要决定。

主闭环完成前不做：

- 多 Agent 并发。
- 完整日历。
- 自动投递。
- 复杂积分或匹配分。
- 社区发布。
- 长期保存原始简历。

    landing

    → result_overview

页面决定：

|---|---|
| 首页 | 要不要开始描述当前困惑 |
| 建档 | 我现在在哪个阶段，想去哪 |

| 结果总览 | 先看观点、来源还是自测 |
| 观点墙 | 哪种判断像我、哪种不适合 |
| 自测 | 我暂时站在哪个位置 |
| 行动路线 | 先验证哪一个小假设 |
| 行动簿 | 现实是否足以改变原判断 |

## 4. 初始化项目

技术栈固定：

- React + Vite：前端状态和界面。
- Node.js ESM：后端代理和静态托管。
- 浏览器本地存储：早期历史记录。
- Railway：常驻 Node 部署。

初始化：

    npm create vite@latest . -- --template react
    npm install
    npm install pdfjs-dist mammoth tesseract.js

目录约定：

    src/                  前端
    server.mjs            后端与静态托管
    zhihu.js              知乎 API 封装
    public/               静态资源
    docs/                 PRD、决策、SOP、提交材料
    scripts/              素材和辅助脚本
    .env.example          环境变量模板
    nixpacks.toml         Railway 构建配置

## 5. 数据模型

### 5.1 处境卡

字段：

    stage, goals, industry, direction, city,
    timePressure, confusion, education, confirmedAt

规则：

- stage、goals、confusion 必填。
- education、city、timePressure 可选。
- 简历解析结果必须用户确认后才可用于推荐。

### 5.2 来源

    {
      id, title, url, source, author, excerpt,
      demo: false, fetchedAt
    }

硬规则：

- 没有 URL 不能标为真实来源。
- demo 为 true 时必须显示“演示素材，不代表真实文章”。
- 不能用虚构答主名包装模型生成内容。

### 5.3 判断记录

    {
      id, topic, card, judgment,
      verification: { action, result, recordedAt },
      memoryDecision: null, createdAt, updatedAt
    }

memoryDecision 只能由用户写入：

- keep：保留。
- revise：修正条件。
- defer：暂不改变。
- release：放下。

## 6. 实现主流程

### 6.1 首页

实现：

- 产品名和一句话价值。
- 标记我的位置主按钮。
- 行动簿入口。
- 登录辅助入口。
- 本地记录导入导出说明。

验收：首屏 5 秒内看懂“这是什么”和“下一步是什么”。

### 6.2 建档

顺序：

1. 当前阶段。
2. 当前目标。
3. 可选经历或简历。
4. 行业、岗位、城市。
5. 当前最想判断什么。

不上传简历也必须完成主流程。补充字段必须说明用途。

### 6.3 处境卡确认

展示系统理解的处境和本次检索范围。主要动作只有：

- 确认路标，开始寻找。
- 调整路标。

### 6.4 检索与异步生成

接口：

- POST /api/alchemy/start：先搜索，返回 jobId、sources、searchStats。
- GET /api/alchemy/status?id=...：轮询观点整理状态。

状态：

| 状态 | 页面行为 |
|---|---|
| searching | 显示正在寻找什么 |
| generating | 显示来源预览和整理进度 |
| complete | 自动补齐观点结果 |
| failed | 保留来源，说明原因并允许重试 |
| JOB_NOT_FOUND | 说明任务过期，允许重新开始 |

前端轮询建议 1.5 秒，提交按钮必须防重复点击。

### 6.5 结果总览

只突出一条路径：

    先看不同声音
    → 辨认自己的倾向
    → 只选一个现实验证

### 6.6 观点墙

固定展示：

- 观点是什么。
- 提出者处境。
- 与我相似。
- 与我不同。
- 可以参考。
- 需要谨慎。
- 真实来源。

用户动作：

- 这部分像我。
- 这个前提不适合我。
- 我还不确定。
- 加入验证。
- 查看真实来源。

联动：

- 像我：影响自测关注点和任务建议。
- 不适合我：降低该观点作为任务的优先级。
- 不确定：保留为待判断。
- 加入验证：写入当前路线。
- 查看来源：新标签页打开 URL。

### 6.7 自测

题目是现实情境，不是知识考试；选项说明不同处境下的代价；反馈先简短展示，深层解释折叠；完成后才生成更具体路线。

### 6.8 行动路线

先给一个短任务，不要一开始输出长计划。

示例：

    投递或联系 3 个明确写着“不限学历”的岗位，
    记录是否进入筛选。

AI 可以准备材料和记录模板，但不能未经确认自动投递或联系。

### 6.9 行动簿

固定链路：

    当时怎么判断
    → 做了什么验证
    → 现实发生了什么
    → 系统提出可能变化
    → 用户确认保留/修正/暂不改变/放下
    → 明确影响下一次使用的方式

判断是主视图，行囊保存可持续成果，不把成果物做成另一组待办事项。

## 7. 接入知乎 API

### 7.1 环境变量

    Copy-Item .env.example .env

最小配置：

    OPENAI_API_KEY=你的知乎开放平台密钥
    OPENAI_BASE_URL=https://developer.zhihu.com/v1
    OPENAI_MODEL=zhida-fast-1p5

登录增强配置：

    ZHIHU_OAUTH_APP_ID=534
    ZHIHU_OAUTH_APP_KEY=你的AppKey
    ZHIHU_OAUTH_REDIRECT_URI=https://你的公网域名/api/auth/callback
    SYNC_STORAGE_KEY=至少32位随机字符串

### 7.2 接口验证

    npm run dev
    Invoke-WebRequest http://localhost:3000/api/health -UseBasicParsing

确认 configured 为 true、reachable 为 true，且剩余额度正常。

### 7.3 来源筛选

保留：有身份、处境、经历、结果和明确前提的内容。

丢弃：无 URL、泛泛建议、标题不相关或真实性无法确认的内容。

### 7.4 额度保护

- 搜索和直答按 query 或 topic 缓存。
- 提交按钮防重复。
- 额度耗尽停止重试。
- fallback 必须明确标注。

## 8. 登录、历史与同步

### 8.1 本地优先

无登录也支持保存、查看、导入和导出行动簿。

### 8.2 登录状态

登录后显示：知乎账号已连接、用户名、行动簿可同步、同步按钮、退出按钮。退出不删除本地记录。

### 8.3 合并规则

本地与云端冲突时：

1. 显示冲突数量。
2. 用户选择是否覆盖。
3. 合并不冲突记录。
4. 不静默删除另一端内容。
5. 同步完成后显示结果。

## 9. UI/UX 最后检查

每个页面检查：

1. 首屏是否说明当前任务。
2. 主按钮是否唯一且明显。
3. 问题、交互、解释、来源是否分层。
4. 点击是否立即产生可见变化。
5. 加载是否说明正在找什么。
6. 失败是否保留已有输入。
7. 空状态是否告诉下一步。
8. 手机是否溢出或遮挡。

Impeccable 顺序：

    critique → audit → clarify → layout → harden → polish

每轮只解决一类问题，完成后重新走主流程。

禁止文案：

- 虚构知乎原文。
- 未经确认的判断变化。
- 用“知乎答主”作为统一身份。
- 与议题无关的人名或标签。
- 没有解释依据的精确匹配分。

## 10. 测试 SOP

### 10.1 自动检查

    npm run build
    node --check server.mjs
    node --check zhihu.js
    git diff --check

### 10.2 本地启动

    npm run dev

前端：http://localhost:5173/

生产模式：

    npm run build
    npm start

### 10.3 人工主流程

完整走：

    首页 → 建档 → 处境卡 → 检索 → 来源预览
    → 观点墙 → 自测 → 行动路线 → 行动簿

逐项确认：来源能打开、演示有标注、按钮有结果、模块有联动、现实结果需确认、登录退出不丢本地记录。

### 10.4 故障处理

- 页面空白：构建、查看控制台、检查 JSX 括号、确认 dist 存在。
- 来源没反应：检查 URL、href 和 click handler；无 URL 就显示不可打开。
- 检索太慢：拆成搜索和观点整理两步，先返回来源，轮询状态，失败保留来源。
- 任务过期：明确提示并允许重新开始。
- GitHub 超时：确认本地提交存在，网络恢复后只执行 git push origin main。

## 11. Railway 部署

根目录准备 nixpacks.toml：

    [phases.install]
    cmds = ["npm ci"]

    [phases.build]
    cmds = ["npm run build"]

    [start]
    cmd = "node server.mjs"

部署：

    railway status
    railway up -s shanwaishan -e production -y --ci

验证首页和 /api/health 均返回 200。

最后一小时禁止换框架、重写 CSS、删除旧接口、替换真实来源或加入大功能。

完成后汇报：改了什么、用户现在能做什么、验证了什么、仍有哪些边界。

## 15. 三天最短复刻路径

第一天：定位、建档、真实来源、结果页、演示兜底。

第二天：观点墙、自测、一个现实验证、历史保存、失败和空状态。

第三天：UI 层级、响应式、登录或导入导出、公网部署、自动检查、材料和队友文档。

新增功能只有在“让主闭环更快、更可信或更可持续”时才加入。

## 16. 最终复刻验收

    [ ] 能一句话说明产品解决的问题
    [ ] 能从零启动本地服务
    [ ] 能验证知乎接口和额度
    [ ] 能先返回来源再异步生成观点
    [ ] 能处理限流、超时、无来源和任务过期
    [ ] 能保存、导入、导出并确认历史判断
    [ ] 能部署 Railway 并验证健康接口
    [ ] 能在手机宽度走完主流程
    [ ] 能生成比赛提交材料
    [ ] 新队友只看本 SOP 就能复现主要链路

## 总原则

先定义判断，再设计界面；先证明来源，再生成观点；先做小步验证，再扩展路线；先让用户确认，再写入长期记忆；先完成可复现交付，再追求额外功能。
