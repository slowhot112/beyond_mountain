# 山外山开发流程复盘与下次复用

> 需要按步骤从零复刻时，请优先阅读 [山外山可复刻开发 SOP](./山外山可复刻开发SOP.md)；本文是背景复盘和方法论说明。

> 项目：山外山 · 知乎求职判断助手
> 
> 目标：把知乎真实经验按用户处境重新组织，帮助用户看见分歧、形成暂时判断，并用一个低成本现实行动验证，而不是替用户直接下结论。
> 
> 这份文档既是本次黑客松的复盘，也是下一次 AI 产品开发可以直接复用的工作方法。

## 1. 最终产品共识

### 1.1 产品内核

山外山不是“替用户选一条路”的推荐器，而是一个判断辅助系统：

```text
真实知乎经验
→ 按用户处境筛选
→ 展示不同立场及适用边界
→ 用户形成暂时判断
→ 完成一个短期现实验证
→ 回到行动簿，记录现实后来告诉了什么
```

核心问题始终是：

> 我当时是怎样判断的？现实后来告诉了我什么？

### 1.2 体验原则

- AI 可以整理材料、解释来源、准备行动，但不能未经确认替用户做关键决定或对外行动。
- 现实证据只能提出变化，不能静默改写用户过去的判断。
- 历史判断不会自动套用到新问题。只有处境相近时，先展示相似条件和差异，再由用户决定是否带入。
- 每个按钮都必须说明下一步会发生什么，不能出现“点完没有变化”。
- 刘看山只在关键节点介入：结果刚生成、用户开始验证、现实结果可能带来变化、用户卡住时。
- 来源必须可打开、可核验。演示素材必须明确标注为演示，不得冒充知乎原文。

### 1.3 视觉与语言

- 知乎生态：克制的知乎蓝、清晰的来源标识、真实内容优先。
- 看山气质：暖白、岩灰、浅蓝山势、脚印、路标、山径、行动簿。
- 暖黄色只用于刘看山、当前脚印和需要注意的变化。
- 不使用黑金、宇宙粒子、3D 星球、无限画布、伪精确匹配分或装饰性 AI 卡片。
- 产品文案不用“炼金”等旧品牌词，统一使用“山径、判断、验证、行动簿、行囊”。

## 2. 本次开发的正确顺序

### 阶段 A：先定产品判断，再写 UI

先回答四个问题：

1. 用户进入产品后，最先要做的一个决定是什么？
2. 产品给出的信息来自哪里，用户能否核验？
3. 用户做完当前动作后，下一步状态如何变化？
4. 这次使用结束后，什么内容会对下一次使用产生影响？

本项目的答案是：

```text
先说清当前困惑
→ 标记当前处境
→ 看真实来源和不同观点
→ 选择像我/不适合/不确定
→ 做一个今天能完成的小验证
→ 把判断和现实结果写进行动簿
```

### 阶段 B：建立最小可用主流程

先只实现一条从头到尾能跑通的路径：

```text
首页
→ 建档
→ 处境卡确认
→ 检索真实来源
→ 观点总览
→ 观点墙
→ 自测
→ 行动路线
→ 行动簿
```

不要先做登录、复杂多 Agent、完整日历、分享社区或动画。它们必须服务主流程，而不能成为主流程的替代品。

### 阶段 C：每个页面只承担一个主要决定

| 页面 | 用户主要决定 | 页面不应该承担 |
|---|---|---|
| 首页 | 要不要开始标记自己的处境 | 解释全部功能 |
| 建档页 | 当前阶段、目标和困惑是什么 | 要求填写完整简历 |
| 处境卡 | 系统将用哪些条件理解我 | 自动判定用户适合什么 |
| 检索过程 | 是否等待结果继续生成 | 让用户面对空白屏 |
| 结果总览 | 先从哪一块开始看 | 把所有模块同时推给用户 |
| 观点墙 | 哪些观点像我、哪些不适合 | 直接替用户选结论 |
| 自测 | 我暂时站在哪个位置 | 伪装成考试并判对错 |
| 行动路线 | 先验证哪一个小假设 | 一开始生成过长计划 |
| 行动簿 | 如何处理现实带来的变化 | 静默覆盖旧判断 |

## 3. 关键产品设计决策

### 3.1 真实来源优先

生成链路采用两步返回：

```text
提交问题
→ 搜索知乎与全网真实来源
→ 立即返回来源预览
→ 后台继续整理观点
→ 前端轮询任务状态
→ 自动补齐观点墙
```

这样做解决了两个问题：

- 用户不会在长时间等待时误以为页面卡死。
- 用户可以先核对真实来源，再看 AI 整理后的观点。

### 3.2 观点不是答主排行榜

观点卡必须按以下层级展示：

1. 观点是什么。
2. 谁在什么处境下提出。
3. 与用户相似的条件。
4. 与用户不同的条件。
5. 哪部分可以参考。
6. 哪部分需要谨慎。
7. 查看真实来源。

避免直接展示容易出戏或误导的名字，例如“汤家凤”“车辆工程考研”“人生修炼手册”这类与当前议题无关的身份标签。系统应展示处境角色，而不是虚构权威。

### 3.3 历史记忆必须由用户控制

行动簿采用“判断 + 行囊”双视图：

- 判断：时间线主视图，记录当时判断、现实验证和变化确认。
- 行囊：保存岗位地图、简历母本、作品、投递记录等可持续成果。

变化确认在卡片内展开，用户可以选择：

- 保留原判断。
- 修正条件。
- 暂不改变。
- 放下这条判断。

每次选择后都必须明确说明：

> 这次选择会如何影响下一次使用。

相似成果合并前必须确认，新增内容不能静默覆盖旧内容。

### 3.4 登录是增强，不是主流程前提

游客模式先完成主流程；登录提供：

- 行动簿跨设备同步。
- 知乎账号已连接状态。
- 同步和退出入口。

退出登录不删除本地记录。云端与本地合并时展示冲突，并由用户决定是否覆盖。

## 4. 技术实现总结

### 4.1 技术栈

- 前端：React 18 + Vite 5。
- 后端：Node.js ESM，`server.mjs` 同时托管静态页面和 API。
- 数据：浏览器本地存储保存行动簿；可选知乎 OAuth + 服务端同步。
- 知乎能力：知乎搜索、全网搜索、知乎直答、额度查询。
- 简历：浏览器端提取 PDF、DOCX、图片、TXT、MD 内容，用户确认后才进入后端结构化。
- 部署：Railway 常驻 Node 服务。

### 4.2 接口设计

主流程接口：

```text
POST /api/alchemy/start
GET  /api/alchemy/status?id=...
POST /api/alchemy
```

账号接口：

```text
GET  /api/auth/config
GET  /api/auth/login
GET  /api/auth/callback
GET  /api/auth/me
POST /api/auth/logout
GET  /api/sync/archive
PUT  /api/sync/archive
```

健康与来源接口：

```text
GET /api/health
GET /api/search?q=...
GET /api/hot
```

### 4.3 可靠性策略

- Secret 缺失时进入明确标注的演示兜底，不白屏。
- 直答超时、限流、额度耗尽时保留真实来源并给出人话提示。
- 搜索、直答和热榜使用缓存，避免重复消耗额度。
- 前端按钮有 disabled、加载、失败、空结果和重试状态。
- 任务状态使用内存 Map，适合比赛演示；长期服务应换成持久化队列或数据库。

## 5. UI/UX 迭代方法

### 5.1 发现问题的顺序

每次看页面都按这个顺序检查：

1. 首屏是否能在 5 秒内说清“这是什么、我下一步做什么”。
2. 信息层级是否能区分问题、交互、解释和来源。
3. 点击后是否有可见变化。
4. 页面之间的状态是否真正联动。
5. 失败、等待、空状态是否可理解。
6. 移动端是否出现溢出、遮挡或按钮难点。
7. 文案是否符合产品内核，是否会误导用户。

### 5.2 本次吸收的参考项目方法

- 人生未定式：单一主入口、强品牌表达、与我相似/不同。
- 故事之外：留白、渐进展示、关键节点把控制权还给用户。
- 活答案：来源状态、人工确认、可追溯更新、不静默覆盖。
- 思想引力场：多观点并置、用户保留判断权。
- 归遥：小步反馈、把复杂目标拆成短任务。
- 问山：上下文贯穿、长期陪伴资产。

吸收方法论，不复制外观。每次借鉴都必须回答：

```text
借鉴了什么机制？
它解决本项目哪个问题？
它会不会破坏山外山的主线？
如何在代码和页面中验证已经实现？
```

## 6. 验收与交付流程

### 6.1 每次改动后的最小检查

```powershell
npm run build
node --check server.mjs
node --check zhihu.js
git diff --check
```

### 6.2 主流程人工回归

至少完整走一遍：

```text
首页 → 建档 → 处境卡 → 检索 → 来源预览 → 观点墙 → 自测 → 行动路线 → 行动簿
```

重点观察：

- 来源链接是否能打开。
- 真实来源和演示内容是否明确区分。
- 点击“查看来源”是否真的有结果。
- 观点标记是否影响自测或行动任务。
- 完成任务后是否进入行动簿。
- 现实结果是否必须经过用户确认才影响下一次使用。
- 登录、同步、退出后本地记录是否仍在。

### 6.3 交付检查

- 公网首页可访问。
- `/api/health` 返回 200 且知乎接口状态可解释。
- 390px、768px、桌面宽度没有明显溢出。
- 封面图为 16:9，ICON 为正方形，均小于 5MB。
- 产品说明计划书、体验链接、代码仓库链接一致。
- GitHub `main` 与本地一致。
- 不在最后阶段引入大范围重构。

## 7. 本次项目的不足与诚实边界

这些不是提交前必须补的功能，而是下一次迭代的风险清单：

1. 异步任务目前存内存，Railway 重启会丢失进行中的任务。
2. 观点生成仍是单次模型调用模拟多角色，不是真正多 Agent 并发。
3. 行动簿已有结构，但长期用户画像和跨项目推荐仍较轻量。
4. 结果页目前是轮询，不是完整 SSE 流式输出。
5. 搜索来源质量依赖知乎 API 返回和模型筛选，需要持续做来源质量抽样。
6. GitHub、Railway、知乎 OAuth 三者的部署配置应在下次用自动化检查统一验证。

## 8. 下一次项目直接复用的模板

### 第 0 天：问题定义

- 写一句话定位。
- 写用户当前最痛的一个决定。
- 写产品明确“不做什么”。
- 选一个最小可验证闭环。

### 第 1 天：主流程

- 画页面状态图，不先画视觉稿。
- 实现输入、结果、来源和错误状态。
- 所有按钮先接上真实结果，再做视觉优化。

### 第 2 天：可信度

- 给每个 AI 结果加来源、条件和不确定性。
- 加人工确认，不允许静默覆盖。
- 增加演示兜底，但显式标注演示内容。

### 第 3 天：体验与交付

- 用真实用户路径走查。
- 用 Impeccable 做层级、布局、响应式和可访问性检查。
- 用测试命令、线上健康检查和手机宽度截图验收。
- 生成封面、ICON、产品说明和队友交接文档。

## 9. 推荐的团队协作方式

每个任务都用下面的格式开工：

```text
目标：这次要改善用户哪一个具体问题？
范围：允许改哪些页面和接口？
不做：明确不碰哪些稳定功能？
验收：用户点击后应该看到什么？
风险：来源、隐私、额度、部署或兼容性风险是什么？
交付：代码、截图、文档、线上地址分别在哪里？
```

每次合并前必须给队友三句话：

1. 我改了什么。
2. 用户现在能做什么以前做不到的事。
3. 我验证了什么，还有什么已知边界。
